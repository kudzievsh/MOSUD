# Практическая работа №11 — Представления, CTE и рекурсивные запросы

**Вариант 3. Корневой штат: MG.**

## Что реализовано

В работе используются производные отношения и рекурсивные запросы PostgreSQL на данных Olist.

1. Создано обычное представление `lab.v_order_summary` — одна строка на заказ с:
   - `order_id`;
   - `customer_state`;
   - временем покупки;
   - количеством позиций;
   - суммой `price + freight_value`.

2. Создано материализованное представление `lab.mv_monthly_state_sales`:
   - месяц;
   - штат;
   - число заказов;
   - сумма продаж.

   В SQL присутствует команда:

   ```sql
   REFRESH MATERIALIZED VIEW lab.mv_monthly_state_sales;
   ```

3. Аналитический запрос разбит минимум на три именованных CTE.

4. Создана иерархия `lab.geo_tree` вида:

   ```text
   BR -> штат -> город
   ```

   Для каждого штата включено не более 20 городов с наибольшим числом клиентов Olist.

5. Для варианта 3 выполнен прямой рекурсивный обход поддерева с корнем `ST:MG`.

6. Выполнен обратный рекурсивный обход для города Belo Horizonte до корня `BR`.

7. Рекурсивно рассчитано количество потомков каждого узла типа `state`.

8. Дополнительно создана временная копия дерева с искусственным циклом и показана защита рекурсии от повторного посещения узлов.

## Схема иерархии

Таблица `lab.geo_tree` содержит:

- `node_id` — первичный ключ узла;
- `parent_id` — внешний ключ на родительский узел этой же таблицы;
- `node_type` — `country`, `state` или `city`;
- `node_name` — имя узла.

Связь является рекурсивной:

```text
geo_tree.parent_id -> geo_tree.node_id
```

Для ветви варианта 3:

```text
Brazil
└── MG
    ├── belo horizonte
    ├── betim
    ├── contagem
    ├── uberlandia
    └── ...
```

В итоговую ветвь MG включено 20 городов.

## Пример `path`

При прямом обходе от MG путь строится, например, как:

```text
MG -> belo horizonte
```

При обратном обходе:

```text
belo horizonte -> MG -> Brazil
```

Поле `path` формируется внутри рекурсивного CTE при каждой итерации.

## Как работает рекурсивный CTE

Рекурсивный CTE состоит из базовой и рекурсивной частей.

### Базовая часть

Она создаёт начальное множество строк. Для обхода варианта 3 выбирается узел:

```sql
WHERE node_id = 'ST:MG'
```

Он получает глубину `0`.

### Рекурсивная часть

Она соединяет уже найденные узлы с их непосредственными потомками:

```sql
JOIN lab.geo_tree AS child
    ON child.parent_id = current.node_id
```

На каждой итерации `depth` увеличивается на 1. Рекурсия завершается, когда больше не находится новых строк.

## Защита от циклов

Для каждого пути хранится массив посещённых идентификаторов:

```sql
ARRAY[node_id]::text[] AS path_ids
```

Перед переходом к следующему узлу проверяется, что он ещё не посещён:

```sql
WHERE NOT child.node_id = ANY(path_ids)
```

Поэтому даже при искусственно созданном цикле рекурсия завершается.

Фактическая проверка дала:

- `safe_walk_rows = 495`;
- `max_depth = 2`;
- `br_occurrences = 1`.

## VIEW и MATERIALIZED VIEW

`VIEW` хранит определение запроса и вычисляет результат при обращении к нему.

`MATERIALIZED VIEW` физически хранит результат. После изменения исходных данных его нужно обновлять командой:

```sql
REFRESH MATERIALIZED VIEW lab.mv_monthly_state_sales;
```

Поэтому обычное представление удобно для всегда актуальных данных, а материализованное — для тяжёлых аналитических агрегатов, которые можно пересчитывать периодически.
